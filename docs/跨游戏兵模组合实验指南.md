# 跨游戏兵模组合实验指南

**版本：1.0**  
**开发者：3136818780（AI 辅助研究与文档整理）**  
**更新日期：2026-08-21**

## 目的与证据边界

本指南用于验证跨游戏替换三件套后“一个部队变成三个、四个或更多部队”的来源。它把实验拆为两个可能相互叠加的层级：**BILE 根动作内部的组合结构**，以及游戏运行时在 BIN 外对同一根动作进行的**上层实例化/阵列选择**。当前工作台已经能严格读取并离线渲染前者，但不会声称仅凭一次截图就能确定后者。

> 工作台的“跨游戏组合实验”不会自动修改游戏目录、`def_motion.xml`、Army 配置或 `def_array.xml`。它只生成候选三件套、精确的单个 Motion 绑定配方、哈希清单与待回填的回归案例，以保证实验变量可追溯。

将军的荣耀3 `unit_infantry` Soldier 待机根动作离线呈现单兵，而世界征服者4对应的组合根动作离线呈现三兵；两者的可复算时间线指标与代表帧见技术说明。[1] 这说明三件套内组合已能解释跨游戏数量差异的一部分，但不取代对游戏上层规则的验证。

## 工作台流程

在目标游戏三件套中选择一个**动画元素**作为目标根动作，再通过“回归 → 生成跨游戏组合实验”选择候选 BIN。工作台会自动要求同目录中的候选 XML 与 WebP/PNG 图集，并列出候选 BIN 内的动画名称供选择。

| 实验输入 | 工作台处理 | 是否写入原文件 |
|---|---|---|
| 目标 BIN / XML / 图集 | 记录 SHA-256、资源基名、BILE 版本和目标根画像。 | 否。 |
| 候选 BIN / XML / 图集 | 以目标三件套的基名暂存至实验 ZIP，并回读候选根动作的三个代表槽位。 | 否。 |
| 候选 XML 的 `<Texture name>` | 只有 XML 明确声明该属性时才改为目标图像文件名；没有该节点则原字节保留。 | 仅写入实验 ZIP 内的候选副本。 |
| `def_motion.xml` | 输出一处 `Motion.name` 的人工绑定配方。 | 否。 |
| `def_array.xml` | 可选地作为只读快照随实验包登记哈希。 | 否。 |

实验 ZIP 旁会生成三个外部审计文件：`*.experiment_manifest.json`、`*.binding_change_recipe.json` 和 `*.validation_report.json`。ZIP 内也包含同内容，便于保留单一归档副本。

## 单变量原则

为把 BIN 内组合与上层实例数区分开，必须保留以下条件不变：游戏版本、资源目标路径、Army/Unit 类型、地图或关卡、单位方向、阵列/Formation 选择和镜头缩放。候选三件套仅用于替换目标基名；随后根据配方只改**一个**对应的 `Motion.name`。不要同时改图集布局、XML 精灵坐标、Army 配置、多个动作名称或阵列坐标。

| 条件 | 固定项 | 唯一处理变量 | 应登记的证据 |
|---|---|---|---|
| A：目标基线 | 原游戏三件套和配置 | 无。 | 同一地图、同一 Army、同一方向的截图/录屏。 |
| B：候选根动作 | 与 A 相同 | 候选三件套与一个 Motion 绑定。 | 与 A 同机位的截图/录屏。 |
| C：上层阵列对照 | 与 B 相同 | 仅改变一个已确认的阵列坐标位。 | 处理前后同机位的截图/录屏和配置哈希。 |

只有 A 与 B 的对照能够说明候选根动作内部组合的影响；只有 B 与 C 的对照才能说明上层阵列是否再实例化整组根动作。若缺少当前游戏版本的 `def_array.xml` 或调用证据，应把 C 标记为未执行，而不是猜测阵列规则。

## 可选 def_array 只读摘要

“回归 → 加载 def_array 阵列摘要”会读取 `Array → Pos` 中的 `soldier` 与 `special` 坐标串，显示每行坐标对数量、源 SHA-256 和结构警告。它只用于固定实验上下文与生成基线/候选差异清单。

> `special` 坐标数恰好等于 `soldier` 坐标数加一时，工作台仅报告这种**形状关系**。这不自动证明最后一个坐标一定是特殊单位，也不证明所有游戏版本使用相同的控制器。

可在命令行进行同样的只读审计：

```bash
python3 tools/inspect_formation_config.py path/to/def_array.xml
python3 tools/inspect_formation_config.py baseline/def_array.xml \
  --candidate candidate/def_array.xml --output-dir research
```

## 游戏内回归案例

生成组合实验包后，工作台会在 ZIP 同目录创建一个回归案例。它使用 `game-regression/v2` 元数据，并要求依次完成备份、基线捕获、替换、单个 Motion 绑定、处理组捕获和恢复。每条截图、录屏或日志都会复制到案例目录并登记 SHA-256。

案例状态应使用下表的含义，不应因“游戏能打开”而直接判定通过。

| 状态 | 使用条件 |
|---|---|
| `pending` | 实验包已生成，尚未在目标游戏执行。 |
| `pass` | 受控条件下的画面和行为符合实验预期，并已保留证据。 |
| `fail` | 出现加载失败、崩溃、错位、闪烁或与预期矛盾的结果。 |
| `inconclusive` | 证据不足、同时发生多变量变化，或无法固定上层条件。 |

## 安全限制

跨游戏组合实验不改变 BILE v2 的只读策略；v2 可作为候选进行解析与离线预览，但其关键帧和锚点写回不开放。BILE v3/v4 的现有保守补丁仍禁止写入 `playback_mode`，不提供新建元素、帧或通道功能。[1]

在运行任何实验前，备份目标目录内的 BIN、XML、图集和可能被手工修改的 `def_motion.xml`。实验包不会包含 APK、签名材料或私钥。离线验证成功只证明候选三件套能被工作台重新读取和渲染，绝不代表目标游戏运行时必然接受。
