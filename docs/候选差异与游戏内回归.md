# 候选差异与游戏内回归

本工作流用于回答一个关键问题：**“这个 BIN 的哪一处被改了、离线画面哪里变了、原游戏是否已经验证过？”** 它将工作台内的暂存编辑、候选 BIN、逐槽位差异、实验包、截图/录屏证据和游戏内结论连接为同一条可审计链路。

## 候选动画差异报告

在工作台完成暂存编辑后，选中目标动画并使用“回归 → 生成候选动画差异报告”。工作台会先执行保存前预检，再将暂存修改实体化为临时候选 BIN，使用与预览相同的 XML/WebP 图集和 `reference_v4` 嵌套时钟逐槽位比较候选与原始动画。

| 输出 | 内容 | 作用 |
|---|---|---|
| `*_animation_diff.json` | 原始/候选 SHA-256、所有槽位像素计数、变更边界、保守字段变化。 | 程序化审计与可重复分析。 |
| `*_animation_diff.md` | 人类可读摘要、变化槽位表和字段差异表。 | 社区讨论、提交记录和人工检查。 |
| `*_slot_XXXX_diff.png` | 原始帧、候选帧、增亮热区的并列图。 | 快速确认变化是否符合预期。 |

差异报告同时保留两种结论。**二进制字段变化**记录 BELE 的仿射矩阵、ARGB、`initial_phase` 以及 BMTI 锚点等保守字段的实值变化；**可见像素变化**记录在当前离线渲染模型和当前画布中被观察到的画面差异。这两个结论不能混为一谈：字段已经改变但当前槽位没有可见变化时，报告会保留字段审计，并如实显示“0 个可见变化槽位”。

> 像素热区证明的是“当前工作台渲染模型下的变化位置”；它不等同于游戏运行时已确认的渲染结果。

## 游戏内回归案例

在存在暂存编辑时，使用“回归 → 创建游戏内回归案例”。工作台会创建一个独立目录，并将候选 BIN 复制到案例目录，因此临时编辑会话关闭后仍可复现案例。

| 文件或目录 | 内容 |
|---|---|
| `candidate.bin` | 绑定此案例的候选 BIN 副本及其 SHA-256。 |
| `candidate_diff/` | 目标动画的 JSON、Markdown 和可见差异热区。 |
| `game_experiment.zip` | 以游戏原始资源名保存的候选三件套与验证报告。 |
| `case.json` | 状态、哈希、目标槽位、设备信息、步骤与证据登记的机器可读记录。 |
| `README_回归案例.md` | 适合人工填写、分享或存档的回归清单。 |
| `evidence/` | 用户导入的截图、录屏或日志副本。 |

案例创建时会把当前播放槽位自动写入“目标槽位”。这是推荐优先截图的位置；必要时可以直接编辑 `case.json` 的 `target_slots`，补充多个整数槽位。案例初始状态为 `pending`，而不是自动标记为通过。

## 登记游戏内证据

在真实设备或模拟器完成替换和触发后，使用“回归 → 登记游戏内截图/录屏证据”，选择案例目录以及截图、录屏或日志文件。工作台会把文件复制到 `evidence/`，记录文件大小、SHA-256、登记时间、类型和说明，并更新案例 README。

推荐在说明中记录触发条件、关卡/单位、游戏版本、资源路径和对比结论。随后可以将案例状态标记为 `pass`、`fail` 或 `inconclusive`；当前工作台保留案例文件格式，便于后续批量状态编辑和社区复现。

| 状态 | 使用条件 |
|---|---|
| `pending` | 已生成候选，但尚未完成游戏内测试。 |
| `pass` | 已在目标游戏版本加载、触发并确认符合预期。 |
| `fail` | 出现加载失败、错位、闪烁、层级错误或其他可复现异常。 |
| `inconclusive` | 已有证据但版本、触发条件或画面不足以得出明确结论。 |

## 建议的最小闭环

先生成候选差异报告，检查字段变化与热区是否符合编辑意图；再创建回归案例和实验包，在目标游戏目录备份后替换三件套；最后登记截图/录屏、填写设备与版本、将状态更新为 `pass`、`fail` 或 `inconclusive`。这样，任何一个社区成员都能根据候选哈希、补丁、差异图和证据文件复查结论。

> 不要将离线差异、候选 BIN 回读成功或实验包生成成功表述为“游戏内验证通过”。只有来自对应游戏版本的加载与触发证据才构成运行时结论。
